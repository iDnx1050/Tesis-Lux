[PERSISTENTE · SEVERIDAD: ALTA]
[CATEGORÍA: A06:2025 — Insecure Design]
[LEY 21.719 — Art. 14 quáter (Privacidad desde el diseño)]
------------------------------------------------------------------------
Archivo: app/checkout/page.tsx:59-61

Problema:
  El cálculo del monto total sigue realizándose completamente en el cliente.
  Los extras se parsean y calculan en el Server Component (líneas 59-61),
  pero la fuente de verdad del precio proviene de un array en memoria
  (lib/mock-data.ts), no de una base de datos. El botón "Confirmar reserva"
  sigue sin integración con Transbank.

Código actual (líneas 59-61):
  const extras = Math.min(3, Math.max(0, parseInt(params.extras ?? '0', 10)))
  const extrasTotal = extras * 60000
  const totalAmount = selectedTier.price + extrasTotal

Riesgo en Fase 2:
  Si este patrón se replica al integrar Transbank enviando `totalAmount`
  desde el cliente, un atacante puede manipular query params para obtener
  precios arbitrarios. El precio enviado a Transbank SIEMPRE debe calcularse
  en el servidor desde la base de datos.

Código corregido para Fase 2 (app/api/checkout/create-session/route.ts):
  export async function POST(req: Request) {
    const { tierId, vedetoSlug, extras } = await req.json()

    // Precio calculado desde BD — el cliente nunca define el monto
    const tier = await prisma.pricingTier.findUniqueOrThrow({
      where: { id: tierId, vedeto: { slug: vedetoSlug } },
    })
    const safeExtras = Math.min(3, Math.max(0, Number(extras) || 0))
    const extrasTotal = safeExtras * 60_000
    const totalAmount = tier.price + extrasTotal

    const tbkResponse = await WebpayPlus.Transaction.create(
      generateBuyOrder(),
      generateSessionId(),
      totalAmount,
      `${process.env.BASE_URL}/api/checkout/confirm`
    )

    return Response.json({ url: tbkResponse.url, token: tbkResponse.token })
  }

Justificación:
  La regla de oro de los pagos: el servidor es la única fuente de verdad
  del precio. Transbank nunca debe recibir un monto calculado en el cliente.

[CATEGORÍA: A01:2025 — Broken Access Control (IDOR latente)]
------------------------------------------------------------------------
Archivo: app/vedetos/[slug]/page.tsx (link a checkout con params URL)

Problema:
  El link de reserva sigue construyendo la URL de checkout con parámetros
  controlados por el usuario (slug, tier, date, time) sin validación de
  pertenencia. En Fase 2 con base de datos, si estos params se usan para
  buscar registros sin validar que el tier pertenece al vedeto indicado,
  constituye un IDOR explotable.

Riesgo en Fase 2:
  Un atacante puede construir manualmente:
  /checkout?slug=vedeto-gratuito&tier=tier-premium-otro-vedeto
  y obtener un checkout con el tier de otro artista al precio del primero.

Código corregido para Fase 2 (Server Component en checkout/page.tsx):
  const vedeto = await prisma.vedeto.findUnique({ where: { slug: params.slug } })
  if (!vedeto) notFound()

  const tier = await prisma.pricingTier.findFirst({
    where: {
      id: params.tier,
      vedetoId: vedeto.id,   // ← Validar pertenencia en BD
    },
  })
  if (!tier) notFound()

Justificación:
  Los parámetros de URL son hints para la UI, no fuente de verdad para
  operaciones con impacto económico. La validación de pertenencia en el
  servidor elimina el IDOR.

[CATEGORÍA: A02:2025 — Security Misconfiguration]
------------------------------------------------------------------------
Archivo: next.config.mjs:31

Problema:
  El Content-Security-Policy incluye 'unsafe-inline' en script-src para
  todos los entornos de producción. Aunque 'unsafe-eval' está correctamente
  restringido a desarrollo, 'unsafe-inline' anula parte de la protección
  XSS que ofrece el CSP.

Código actual (línea 31):
  `script-src 'self' 'unsafe-inline'${isDev ? " 'unsafe-eval'" : ''}`

Impacto:
  Cualquier XSS reflejado o almacenado puede ejecutar scripts inline sin
  que el CSP los bloquee. Esto es especialmente relevante en Fase 2 cuando
  haya inputs de usuario (formulario de registro, búsquedas).

Código corregido para Fase 2 (nonce-based CSP en middleware.ts):
  import { NextResponse } from 'next/server'
  import { randomBytes } from 'crypto'

  export function middleware(request: Request) {
    const nonce = randomBytes(16).toString('base64')
    const response = NextResponse.next()

    response.headers.set(
      'Content-Security-Policy',
      [
        "default-src 'self'",
        `script-src 'self' 'nonce-${nonce}'`,
        "style-src 'self' 'unsafe-inline' https://fonts.googleapis.com",
        "font-src 'self' https://fonts.gstatic.com",
        "img-src 'self' data: blob: https://images.unsplash.com",
        "connect-src 'self'",
        "frame-ancestors 'none'",
      ].join('; ')
    )
    response.headers.set('x-nonce', nonce)
    return response
  }

Justificación:
  Con nonce-based CSP, solo los scripts con el nonce correcto (generado
  por request) se ejecutan. Esto bloquea XSS inline incluso si un atacante
  inyecta código malicioso.

[CATEGORÍA: A06:2025 — Insecure Design]
[LEY 21.719 — Art. 2 (Datos sensibles) / Verificación de edad]
------------------------------------------------------------------------
Archivo: components/age-gate.tsx:19-22

Problema:
  La verificación de edad se apoya en una cookie de sesión sin firma HMAC.
  Cualquier usuario técnico puede crear la cookie manualmente en DevTools:
    document.cookie = 'luxx_age_verified=true; path=/'
  y bypassear el age gate sin ver la pantalla de verificación.

Código actual (línea 21):
  document.cookie = `${COOKIE_NAME}=${COOKIE_VALUE}; path=/; SameSite=Strict; Secure`

Impacto:
  El age gate es bypasseable trivialmente. Para contenido adulto sujeto a
  Ley 21.719 Art. 2 (datos sensibles de vida sexual), la verificación de
  edad es un requisito de protección, no solo UI. Un menú de 10 segundos
  en DevTools anula la barrera.

  Nota: ninguna cookie de sesión del lado cliente ofrece protección real
  de edad (requiere verificación de identidad oficial). Sin embargo, una
  cookie firmada eleva el esfuerzo técnico necesario para el bypass.

Código corregido (verificación firmada en servidor — Fase 2):
  // app/api/age-verify/route.ts
  import { SignJWT } from 'jose'

  export async function POST() {
    const secret = new TextEncoder().encode(process.env.AGE_GATE_SECRET)
    const token = await new SignJWT({ verified: true })
      .setProtectedHeader({ alg: 'HS256' })
      .setExpirationTime('24h')
      .sign(secret)

    const response = new Response(JSON.stringify({ ok: true }))
    response.headers.set(
      'Set-Cookie',
      `luxx_av=${token}; Path=/; HttpOnly; SameSite=Strict; Secure; Max-Age=86400`
    )
    return response
  }

Justificación:
  Una cookie HttpOnly firmada con JOSE/HS256 no es accesible desde JS
  del cliente (elimina XSS de robo de cookie) y no puede fabricarse sin
  conocer el secreto del servidor. En Fase 2 puede complementarse con
  verificación de RUT vía Registro Civil.

[CATEGORÍA: A02:2025 — Security Misconfiguration]
------------------------------------------------------------------------
Archivo: netlify.toml

Problema:
  El netlify.toml no declara headers HTTP de seguridad. Los headers están
  definidos en next.config.mjs (vía la función async headers()), pero el
  plugin @netlify/plugin-nextjs solo garantiza su propagación para rutas
  SSR/Server Components. Los archivos verdaderamente estáticos del directorio
  /_next/static/ y el favicon no pasan por el runtime de Next.js y por tanto
  podrían servirse sin los headers de seguridad.

Código actual (netlify.toml):
  [build]
    command = "npm run build"
    publish = ".next"
  [[plugins]]
    package = "@netlify/plugin-nextjs"
  # ← Sin sección [[headers]]

Código corregido (agregar en netlify.toml):
  [[headers]]
    for = "/*"
    [headers.values]
      X-Frame-Options = "DENY"
      X-Content-Type-Options = "nosniff"
      Referrer-Policy = "strict-origin-when-cross-origin"
      Permissions-Policy = "camera=(), microphone=(), geolocation=()"
      Strict-Transport-Security = "max-age=31536000; includeSubDomains"

  # Los assets estáticos de Next.js son inmutables — cache agresivo
  [[headers]]
    for = "/_next/static/*"
    [headers.values]
      Cache-Control = "public, max-age=31536000, immutable"

Justificación:
  Netlify aplica los headers de next.config.mjs a través del plugin, pero
  declarar los headers también en netlify.toml garantiza cobertura para
  cualquier asset que no pase por el runtime de Next.js, incluyendo
  redirects 301/302 a nivel CDN y el archivo favicon.ico.

[CATEGORÍA: A03:2025 — Software and Data Integrity (validación de input)]
------------------------------------------------------------------------
Archivo: app/checkout/page.tsx:59

Problema:
  El parámetro `extras` de la URL se parsea con parseInt(), pero si el
  valor no es un número válido (ej: extras=abc), parseInt devuelve NaN.
  La cadena de cálculo NaN + 60000 = NaN hace que `totalAmount` sea NaN,
  lo que se muestra en la UI formateado como "$NaN" o "$0" según el
  navegador.

Código actual (línea 59):
  const extras = Math.min(3, Math.max(0, parseInt(params.extras ?? '0', 10)))

  // Si params.extras = "abc":
  // parseInt("abc", 10) → NaN
  // Math.max(0, NaN)    → NaN  (Math.max con NaN devuelve NaN)
  // Math.min(3, NaN)    → NaN
  // extrasTotal = NaN * 60000 = NaN
  // totalAmount = precio + NaN = NaN

Código corregido (línea 59):
  const rawExtras = parseInt(params.extras ?? '0', 10)
  const extras = Number.isNaN(rawExtras) ? 0 : Math.min(3, Math.max(0, rawExtras))

Justificación:
  La guardia explícita con Number.isNaN() previene que un parámetro
  malformado llegue al cálculo. Es una corrección de 2 líneas que puede
  aplicarse ahora en Fase 1.

[NUEVO · SEVERIDAD: BAJA]
[CATEGORÍA: A01:2025 — Broken Access Control]
------------------------------------------------------------------------
Archivo: (ausente) — middleware.ts no existe en el proyecto

Problema:
  No existe un middleware.ts en la raíz del proyecto. Sin él, todas las
  rutas del sitio son públicamente accesibles en Fase 2, incluyendo las
  rutas de administración (/admin/*) y operaciones de pago.

Impacto en Fase 2:
  Sin middleware que valide la sesión NextAuth, cualquier usuario puede
  acceder a rutas protegidas simplemente conociendo la URL.

Esqueleto requerido para Fase 2 (middleware.ts):
  import { withAuth } from 'next-auth/middleware'

  export default withAuth({
    pages: { signIn: '/login' },
  })

  export const config = {
    matcher: [
      '/admin/:path*',
      '/api/checkout/:path*',
      '/api/admin/:path*',
    ],
  }

Justificación:
  El middleware de NextAuth verifica el token de sesión en el Edge antes
  de que la request llegue al Server Component, bloqueando acceso no
  autorizado sin costo de rendering.
