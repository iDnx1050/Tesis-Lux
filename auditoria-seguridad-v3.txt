[CATEGORÍA: A02:2025 — Security Misconfiguration]
------------------------------------------------------------------------
Archivos: next.config.mjs:15  ·  proxy.ts (completo)  ·  netlify.toml
          middleware.ts (INEXISTENTE)

Problema:
  El proyecto NO envía ningún header Content-Security-Policy en producción.
  En v2 el CSP existía dentro de next.config.mjs (con 'unsafe-inline'). En el
  avance 3 ese CSP fue ELIMINADO y sustituido por un comentario que promete una
  implementación que no existe:

  next.config.mjs:15
    // CSP y headers de seguridad se gestionan en middleware.ts con nonce
    // dinámico. [...]

  Se verificó que:
    1. No existe ningún archivo middleware.ts / middleware.js en el repositorio
       (solo el artefacto de build .next/dev/server/middleware.js, generado a
       partir de proxy.ts).
    2. Next.js 16.2.11 reconoce el archivo proxy.ts como convención de middleware
       (PROXY_FILENAME = 'proxy' en node_modules/next/dist/lib/constants.js), por
       lo que proxy.ts SÍ se ejecuta... pero solo asigna un x-request-id:

       proxy.ts:4-9
         export function proxy(request: NextRequest) {
           const response = NextResponse.next()
           const requestId = crypto.randomUUID()
           response.headers.set('x-request-id', requestId)
           return response
         }

    3. netlify.toml declara X-Frame-Options, HSTS, etc., pero TAMPOCO incluye
       Content-Security-Policy.

  Resultado: la política CSP que protegía contra XSS/inyección de recursos
  desapareció en las tres capas posibles (config, proxy/middleware, CDN).

Impacto:
  El CSP es la capa de defensa en profundidad principal contra XSS. Su ausencia
  es especialmente relevante en un sitio de contenido adulto que en Fase 2
  incorporará formularios de registro, búsquedas y datos de usuario. El
  comentario en next.config.mjs es peor que no tener nada: induce a un
  mantenedor a creer que el CSP está cubierto por un middleware que no existe.

Código corregido (implementar el CSP prometido en proxy.ts con nonce):
  // proxy.ts
  import { NextResponse } from 'next/server'
  import type { NextRequest } from 'next/server'

  export function proxy(request: NextRequest) {
    const nonce = Buffer.from(crypto.randomUUID()).toString('base64')

    const csp = [
      "default-src 'self'",
      `script-src 'self' 'nonce-${nonce}'${process.env.NODE_ENV !== 'production' ? " 'unsafe-eval'" : ''}`,
      "style-src 'self' 'unsafe-inline'",           // requerido por Tailwind
      "img-src 'self' data: blob: https://images.unsplash.com https://*.tile.openstreetmap.org",
      "font-src 'self'",
      "frame-src https://www.openstreetmap.org https://maps.google.com",
      "connect-src 'self' https://nominatim.openstreetmap.org",
      "frame-ancestors 'none'",
      "base-uri 'self'",
      "form-action 'self'",
    ].join('; ')

    const response = NextResponse.next()
    response.headers.set('x-request-id', crypto.randomUUID())
    response.headers.set('x-nonce', nonce)
    response.headers.set('Content-Security-Policy', csp)
    return response
  }

  export const config = {
    matcher: ['/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)'],
  }

Justificación:
  El CSP debe reintroducirse ya, aunque sea sin nonce (con 'unsafe-inline' como
  en v2) mientras se migra. Un CSP imperfecto protege más que ningún CSP. Si el
  nonce complica los estilos inline de Tailwind/framer-motion en el corto plazo,
  al menos restaurar el CSP básico y CORREGIR el comentario de next.config.mjs
  para que refleje la realidad.

[CATEGORÍA: A06:2025 — Vulnerable and Outdated Components]
------------------------------------------------------------------------
Archivo: package-lock.json (dependencias transitivas de next)

Problema:
  `npm audit --omit=dev` reporta 3 vulnerabilidades de severidad ALTA en el
  árbol de dependencias de producción:

  1. sharp <0.35.0  — vulnerabilidades heredadas de libvips
     CVE-2026-33327, CVE-2026-33328, CVE-2026-35590, CVE-2026-35591
     (GHSA-f88m-g3jw-g9cj). sharp es usado por next/image para optimizar
     imágenes EN TIEMPO DE EJECUCIÓN.

  2. postcss <=8.5.11 — XSS vía </style> sin escapar en la salida del
     stringify (GHSA-qx2v-qp2m-jg93) y lectura arbitraria de archivos /
     divulgación de información vía sourceMappingURL controlable por atacante
     en comentarios CSS (GHSA-6g55-p6wh-862q).

Impacto:
  - sharp: procesa imágenes en el servidor. La superficie práctica está acotada
    porque las imágenes remotas provienen de un remotePatterns fijo
    (images.unsplash.com) y de assets locales — un atacante no controla la
    fuente de imágenes. Aun así es un CVE de severidad alta activo en el runtime.
  - postcss: es principalmente una dependencia de build; el riesgo se materializa
    si se procesa CSS de origen no confiable.

IMPORTANTE — no ejecutar la corrección que sugiere npm:
  `npm audit fix --force` propone instalar next@9.3.3 (¡downgrade destructivo de
  7 versiones mayores!). NO hacerlo. La corrección correcta es una de estas:

  Opción A (preferida) — actualizar Next.js a un parche que arrastre versiones
  sanas de sharp/postcss:
    npm install next@latest

  Opción B — forzar las versiones parcheadas con overrides en package.json:
    "overrides": {
      "sharp": ">=0.35.0",
      "postcss": ">=8.5.12"
    }
  Luego: npm install && npm audit --omit=dev  (debe reportar 0 vulnerabilidades)

Justificación:
  A06 (componentes vulnerables) fue un hallazgo CRÍTICO en v1 (swiper, next) que
  se cerró correctamente. Mantener `npm audit` limpio es una disciplina de
  higiene continua, no un evento único. Documentar en la tesis la diferencia
  entre la corrección correcta (override/upgrade) y la que sugiere la herramienta
  (downgrade destructivo) es un buen punto de análisis.

[CATEGORÍA: A07:2025 — Identification and Authentication Failures]
[LEY 21.719 — Verificación de edad / datos sensibles Art. 2]
------------------------------------------------------------------------
Archivos: app/api/age-verify/route.ts:12  ·  components/age-gate.tsx:14-18

Problema:
  El avance 3 implementó un age gate "de servidor" con cookie HttpOnly firmada
  con HMAC (luxx_av) — buena intención y respuesta directa al hallazgo v2. PERO
  la función que verifica esa firma NUNCA se ejecuta:

  app/api/age-verify/route.ts:12
    export function verifyToken(token: string): boolean { ... }

  Se verificó por búsqueda en todo el repositorio: `verifyToken` se DEFINE y se
  EXPORTA, pero no se importa ni se invoca en ningún otro archivo. No hay
  middleware ni Server Component que lea la cookie luxx_av y bloquee el contenido.

  El único control que decide si se muestra el sitio vive en el cliente y lee la
  OTRA cookie, la no-firmada y legible por JS:

  components/age-gate.tsx:14-18
    useEffect(() => {
      const cookies = document.cookie.split(';').map((c) => c.trim())
      const found = cookies.some((c) => c.startsWith(`${UI_COOKIE}=`))  // luxx_av_ui
      setVerified(found)
    }, [])

Impacto:
  El age gate se bypassa exactamente igual que en v2 — no se corrigió, solo se
  disfrazó. Cualquiera puede ejecutar en la consola del navegador:
      document.cookie = 'luxx_av_ui=1; path=/'
  o simplemente llamar `fetch('/api/age-verify', {method:'POST'})` una vez.
  La cookie firmada luxx_av es teatro de seguridad: se emite pero nadie la valida.
  El comentario en age-gate.tsx:8 ("la cookie HttpOnly firmada con HMAC que el
  servidor verifica") es FALSO — el servidor no la verifica.

Código corregido (verificar la firma en proxy.ts y proteger las rutas):
  // proxy.ts — reutilizar la lógica HMAC, mover verifyToken a lib/age-gate.ts
  import { verifyAgeToken } from '@/lib/age-gate'

  export function proxy(request: NextRequest) {
    const isContent = !request.nextUrl.pathname.startsWith('/api/age-verify')
    const token = request.cookies.get('luxx_av')?.value
    if (isContent && (!token || !verifyAgeToken(token))) {
      // renderizar/redirigir a la pantalla de verificación server-side
      return NextResponse.rewrite(new URL('/verificar-edad', request.url))
    }
    return NextResponse.next()
  }

Justificación:
  Un control de seguridad que existe pero no se ejecuta es peor que su ausencia:
  crea la ilusión de estar protegido. Para contenido adulto sujeto a Ley 21.719,
  la verificación debe ocurrir en el servidor antes de servir el contenido.
  (Nota honesta para la tesis: ninguna cookie ofrece verificación de edad REAL;
  requiere verificación de identidad. Pero al menos la barrera debe ser efectiva
  del lado servidor, no un overlay client-side saltable en 5 segundos.)

[CATEGORÍA: A02:2025 — Security Misconfiguration]
------------------------------------------------------------------------
Archivo: app/api/age-verify/route.ts:4

Problema:
  El secreto de firma HMAC tiene un valor por defecto hardcodeado y público:

  app/api/age-verify/route.ts:4
    const SECRET = process.env.AGE_GATE_SECRET ?? 'dev-secret-change-in-production'

  Dos problemas:
    1. Si AGE_GATE_SECRET no está definido en producción, se firma con un secreto
       conocido por cualquiera que lea el código → los tokens son falsificables.
    2. TRAMPA DEL OPERADOR ??: en .env.example la variable está declarada vacía
       (AGE_GATE_SECRET=). Si se despliega con ese valor, `process.env.AGE_GATE_SECRET`
       es la cadena vacía "", que NO es null/undefined, por lo que `??` la conserva.
       Resultado: se firmaría con clave vacía "" — aún peor que el default.

Impacto:
  Actualmente atenuado porque el token no se verifica en ningún lado (ver hallazgo
  anterior), pero es una mina: en cuanto se cablee verifyToken, un secreto vacío o
  por defecto hace que la firma no proteja nada.

Código corregido:
  const SECRET = process.env.AGE_GATE_SECRET
  if (!SECRET || SECRET.length < 32) {
    throw new Error('AGE_GATE_SECRET faltante o demasiado corto (mín. 32 bytes)')
  }

Justificación:
  Un secreto de firma debe fallar de forma RUIDOSA si falta, nunca degradar
  silenciosamente a un valor conocido. La validación de longitud mínima obliga a
  usar el `openssl rand -base64 32` que el propio .env.example documenta.

[CATEGORÍA: A04:2025 — Insecure Design (rate limiting inefectivo)]
------------------------------------------------------------------------
Archivos: lib/rate-limiter.ts:10,42  ·  app/api/bookings/route.ts:13

Problema (dos causas que se combinan):

  1. ALMACÉN EN MEMORIA POR INSTANCIA. El rate limiter usa un Map en memoria del
     proceso (lib/rate-limiter.ts:10). El propio archivo lo advierte en un
     comentario. En Netlify (funciones serverless) cada invocación puede correr en
     una instancia distinta o en un cold start que reinicia el Map, por lo que el
     límite de "3 reservas por IP por hora" es en la práctica ineficaz. Además el
     setInterval de limpieza (línea 42) no tiene garantía de ejecución en un
     entorno serverless efímero.

  2. CLAVE BASADA EN UN HEADER FALSIFICABLE. La IP se toma del primer valor de
     X-Forwarded-For, que el cliente controla:

     app/api/bookings/route.ts:13
       const ip = req.headers.get('x-forwarded-for')?.split(',')[0].trim() ?? 'unknown'

     Un atacante rota el header en cada petición:
       X-Forwarded-For: 1.1.1.1  →  clave booking:1.1.1.1
       X-Forwarded-For: 1.1.1.2  →  clave booking:1.1.1.2  (contador nuevo)
     y evade el límite por completo.

Impacto:
  El rate limiting da una falsa sensación de protección. En Fase 2, cuando exista
  login, este mismo patrón dejaría el endpoint de autenticación sin protección
  real contra fuerza bruta / credential stuffing.

Código corregido:
  - Producción multi-instancia: usar un store compartido (Upstash Redis / Vercel KV;
    .env.example ya documenta UPSTASH_REDIS_REST_URL). El Map en memoria solo sirve
    para desarrollo local.
  - Obtener la IP de una fuente confiable de la plataforma. En Netlify:
      import { getStore } from '@netlify/...'  // o el header que Netlify garantiza
    Como mínimo, tomar el ÚLTIMO valor de X-Forwarded-For (el que agrega el proxy
    de confianza), no el primero (el que pone el cliente):
      const xff = req.headers.get('x-forwarded-for')?.split(',').map(s => s.trim())
      const ip = xff?.[xff.length - 1] ?? 'unknown'

Justificación:
  Un rate limiter solo es tan fuerte como su clave y su persistencia. Si la clave
  la controla el atacante o el contador se reinicia con cada cold start, el control
  no cumple su función.

[CATEGORÍA: A09:2025 — Security Logging and Monitoring Failures]
[LEY 21.719 — Art. 2 (datos personales / sensibles), Art. 14 quáter]
------------------------------------------------------------------------
Archivos: app/api/bookings/route.ts:64-72  ·  lib/logger.ts:23-41

Problema:
  El logger sanitiza claves sensibles, lo cual es correcto, pero:

  1. La lista SENSITIVE_KEYS (lib/logger.ts:23-35) NO incluye datos personales
     que sí maneja la app: `ip`, `email`, `contactEmail`, `phone`, `contactPhone`,
     `address`. Si alguno de esos campos se pasa a un log en el futuro, se filtra.

  2. Hoy ya se registra la IP del cliente asociada a una reserva de contenido
     adulto:

     app/api/bookings/route.ts:64-72
       logSecurityEvent('BOOKING_CREATED', { ip, bookingId, vededoSlug, tierId, date })
       logRequest('POST', '/api/bookings', 201, ..., { ip, bookingId })

     La IP es dato personal bajo la Ley 21.719. La combinación IP + reserva de un
     show de contenido adulto puede considerarse dato sensible (Art. 2, vida
     sexual/orientación inferida). Esos logs van a `console.log`, que en Netlify
     se retiene en los logs de la función sin los controles de retención/cifrado
     que la ley exige para datos sensibles.

  3. La sanitización es por coincidencia EXACTA de clave (Set.has) y case-sensitive:
     no cubre variantes como `userEmail`, `Email`, ni objetos anidados (aunque el
     tipo LogMetadata hoy solo permite valores primitivos, lo cual lo mitiga).

Impacto:
  Registro de datos personales/sensibles en claro en un destino de logs sin
  política de retención — riesgo de incumplimiento de la Ley 21.719 y superficie
  de fuga si los logs se exponen.

Código corregido:
  - Ampliar SENSITIVE_KEYS con: 'ip','email','contactEmail','phone','contactPhone',
    'address','direccion','telefono'.
  - Para trazabilidad sin exponer la IP completa, hashearla o truncarla:
      const ipHash = createHash('sha256').update(ip + SALT).digest('hex').slice(0,12)
      logSecurityEvent('BOOKING_CREATED', { ipHash, bookingId, ... })
  - Definir política de retención de logs (p. ej. 90 días) y documentarla.

Justificación:
  El logging de seguridad debe permitir investigar incidentes SIN convertirse él
  mismo en un repositorio de datos personales. Hashear/truncar la IP conserva la
  capacidad de correlación (misma IP → mismo hash) sin almacenar el dato personal.

[CATEGORÍA: A02:2025 — Security Misconfiguration (comparación no constante)]
------------------------------------------------------------------------
Archivo: app/api/age-verify/route.ts:16-21

Problema:
  La verificación del token usa comparación de strings con === :
    return token === expected
  No es de tiempo constante; en teoría es susceptible a un ataque de temporización.

Impacto:
  Muy bajo (y hoy nulo, porque verifyToken ni siquiera se invoca). Un ataque de
  temporización sobre HMAC vía red es poco práctico, pero es una mala práctica
  criptográfica que conviene corregir al cablear la verificación.

Código corregido:
  import { timingSafeEqual } from 'crypto'
  const a = Buffer.from(token); const b = Buffer.from(expected)
  return a.length === b.length && timingSafeEqual(a, b)

Justificación:
  Toda comparación de secretos/MAC debe ser de tiempo constante por principio,
  aunque el riesgo específico sea bajo.

[LEY 21.719 — Transferencia a terceros]
------------------------------------------------------------------------
Archivo: components/address-map-section.tsx:59-68, 94-98

Problema:
  Mientras el usuario escribe su dirección, el componente la envía (con debounce
  de 450 ms) directamente desde el navegador a Nominatim de OpenStreetMap:
    const url = `https://nominatim.openstreetmap.org/search?q=${encodeURIComponent(query)}...`
  y luego embebe un iframe de openstreetmap.org o maps.google.com con la dirección.

  La consulta está correctamente URL-encoded (no hay inyección). El punto es de
  PRIVACIDAD: la dirección del evento —un dato personal— se transmite a servicios
  de terceros (uno de ellos, Google, fuera de Chile) sin aviso ni base de licitud.

Impacto:
  Transferencia de datos personales a terceros sin consentimiento informado
  (relevante bajo Ley 21.719). Además, la política de uso de Nominatim exige
  identificarse y limitar el volumen; usarla como autocompletado desde muchos
  clientes puede violar sus términos.

Recomendación:
  - Añadir un aviso ("la búsqueda de direcciones usa OpenStreetMap") o hacer el
    geocoding vía un proxy propio en el servidor con rate limiting y User-Agent
    identificado.
  - Incluir estas transferencias en la política de privacidad.

Justificación:
  No es una vulnerabilidad de inyección, sino de cumplimiento y minimización de
  datos — pertinente para el marco legal de la tesis.

[CATEGORÍA: A03:2025 — Injection / robustez de entrada]
------------------------------------------------------------------------
Archivos: app/api/bookings/route.ts:24  ·  lib/validations.ts

Problema:
  Las rutas de API leen el cuerpo con `await req.json()` sin un límite de tamaño
  propio antes de validar. La validación de email usa
    EMAIL_RE = /^[^\s@]+@[^\s@]+\.[^\s@]+$/
  sin acotar la longitud del string de entrada previamente.

Aclaración honesta (para no inflar el hallazgo):
  Se analizó esta regex por posible ReDoS. Su estructura (grupos separados por
  anclas literales @ y \.) produce backtracking LINEAL, no catastrófico — NO es
  un ReDoS explotable. El único costo real de una entrada gigante sería memoria
  al bufferizar el JSON, y Netlify ya impone un límite de tamaño de cuerpo a nivel
  de plataforma (~6 MB). Por eso es BAJA, no media.

Recomendación (defensa en profundidad):
  - Rechazar cuerpos grandes temprano:
      const len = Number(req.headers.get('content-length') ?? 0)
      if (len > 10_000) return apiError('Cuerpo demasiado grande', 413)
  - Acotar la longitud de cada campo antes de aplicar regex (p. ej. email <= 254).

Justificación:
  Validar tamaño antes de contenido es una buena práctica que evita trabajo
  innecesario y cierra vectores de agotamiento de recursos de raíz.
