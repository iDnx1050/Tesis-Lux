[CATEGORÍA: A02:2025 — Security Misconfiguration]
------------------------------------------------------------------------
Archivo: next.config.mjs:3-5

Problema:
  typescript.ignoreBuildErrors: true desactiva la verificación de tipos durante
  el build de producción. TypeScript en Next.js actúa como primera línea de
  defensa contra tipos de datos inesperados que podrían llegar a queries de
  base de datos, validaciones de roles y flujos de pago.

Impacto:
  Cuando se integre Prisma, esta configuración puede permitir que código con
  errores de tipo llegue a producción, habilitando potencialmente injection vía
  tipado inseguro o bypass de validaciones de rol.

Código actual:
  typescript: {
    ignoreBuildErrors: true,
  },

Código corregido:
  // Eliminar el bloque completo, o establecer explícitamente:
  typescript: {
    ignoreBuildErrors: false,
  },

Justificación:
  Forzar errores de compilación en CI garantiza que ningún código con tipos
  incorrectos llegue al servidor de producción.

Archivo: next.config.mjs (ausencia total de headers HTTP de seguridad)

Problema:
  El proyecto no configura ningún header HTTP de seguridad. La ausencia de CSP,
  HSTS, X-Frame-Options y X-Content-Type-Options deja al sitio expuesto a
  clickjacking, MIME sniffing, y XSS reflejado.

Impacto:
  Sin X-Frame-Options: DENY, el sitio puede embeberse en un iframe malicioso
  para ataques de clickjacking sobre el botón "Confirmar reserva". Sin CSP,
  cualquier XSS inyectado puede exfiltrar datos del formulario de pago al
  agregarse el backend.

Código actual:
  const nextConfig = {
    typescript: { ignoreBuildErrors: true },
    images: { ... },
    compress: true,
    poweredByHeader: false,
    // ← sin sección headers()
  }

Código corregido (agregar en next.config.mjs):
  async headers() {
    return [
      {
        source: '/:path*',
        headers: [
          { key: 'X-Frame-Options', value: 'DENY' },
          { key: 'X-Content-Type-Options', value: 'nosniff' },
          { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
          { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
          { key: 'Strict-Transport-Security', value: 'max-age=31536000; includeSubDomains' },
          {
            key: 'Content-Security-Policy',
            value: [
              "default-src 'self'",
              "script-src 'self' 'unsafe-inline' https://va.vercel-scripts.com",
              "style-src 'self' 'unsafe-inline' https://fonts.googleapis.com",
              "font-src 'self' https://fonts.gstatic.com",
              "img-src 'self' data: https://images.unsplash.com",
              "connect-src 'self' https://vitals.vercel-insights.com",
              "frame-ancestors 'none'",
            ].join('; '),
          },
        ],
      },
    ]
  },

Justificación:
  Los 6 headers cubren los vectores de ataque más comunes. El CSP propuesto es
  el mínimo funcional — en Fase 2 debe migrar a nonce-based CSP para eliminar
  'unsafe-inline'.

[LEY 21.719 — Art. 14 quáter (Privacidad desde el diseño)]
------------------------------------------------------------------------
Archivo: app/checkout/page.tsx:195-251

Problema:
  La página de checkout presenta un formulario de tarjeta de crédito con campos
  para Titular, Número de tarjeta, Vencimiento y CVV, acompañado de badges
  "Pago seguro" y "Conexión cifrada". Sin embargo, el botón "Confirmar reserva"
  tiene type="button" y NO tiene ningún manejador de eventos ni action: no envía
  datos a ningún servidor, no integra Transbank ni ningún procesador de pagos.

Impacto:
  1. UX deceptiva con consecuencias legales: Un usuario puede creer que está
     completando una transacción real. Esto viola el principio de privacidad
     desde el diseño (Art. 14 quáter) y podría constituir publicidad engañosa
     bajo la Ley 19.496 (consumidor).
  2. Patrón inseguro para Fase 2: El monto se calcula en el frontend (líneas
     57-58). Si se replica al integrar Transbank, un atacante puede manipular
     los query params para obtener precios alterados.

Código actual (líneas 57-58):
  const logisticsFee = Math.round(selectedTier.price * 0.08)
  const totalAmount = selectedTier.price + logisticsFee

Código actual (líneas 246-251):
  <button
    type="button"
    className="w-full rounded-2xl bg-[...] ..."
  >
    Confirmar reserva
  </button>

Código corregido para Fase 2 (app/api/checkout/create-session/route.ts):
  export async function POST(req: Request) {
    const { tierId, vedetoSlug } = await req.json()

    // Lookup canónico desde la base de datos — el cliente NO define el precio
    const tier = await prisma.pricingTier.findUniqueOrThrow({ where: { id: tierId } })
    const logisticsFee = Math.round(tier.price * 0.08)
    const totalAmount = tier.price + logisticsFee

    // Iniciar sesión Transbank con el monto calculado en servidor
    const tbkResponse = await WebpayPlus.Transaction.create(
      generateBuyOrder(),
      generateSessionId(),
      totalAmount,
      `${process.env.BASE_URL}/api/checkout/confirm`
    )

    return Response.json({ url: tbkResponse.url, token: tbkResponse.token })
  }

Justificación:
  La regla de oro de los pagos: el servidor es la fuente de verdad del precio.
  Transbank nunca debe recibir un monto que provenga del frontend sin validación
  backend.

Archivo: app/vedetos/[slug]/page.tsx:359-365

Problema:
  El link de reserva construye la URL de checkout concatenando directamente
  parámetros controlados por el usuario (slug, tier, date, time) sin validación
  adicional. En Fase 2, si estos parámetros se usan para buscar registros en DB

Impacto:
  Un atacante podría manipular ?tier=p1&slug=admin-vedeto para reservar un

Código actual (línea 360-362):
  href={`/checkout?slug=${vedeto.slug}&tier=${selectedTier.id}${selectedDate ?
  `&date=${selectedDate}` : ''}${selectedTime ? `&time=${selectedTime}` : ''}`}

Código corregido para Fase 2 (app/checkout/page.tsx — Server Component):
  const vedeto = await prisma.vedeto.findUnique({ where: { slug: params.slug } })
  if (!vedeto) notFound()

  const tier = await prisma.pricingTier.findFirst({
    where: {
      id: params.tier,
      vedetoId: vedeto.id, // ← Validar que el tier pertenece a ESTE vedeto
    },
  })
  if (!tier) notFound()

Justificación:
  Validar la pertenencia del recurso en servidor elimina el IDOR. Los params de
  URL son hints para la UI, no fuente de verdad para operaciones.

[CATEGORÍA: A09:2025 — Security Logging and Monitoring Failures]
------------------------------------------------------------------------
Archivo: Todo el proyecto (ausencia)

Problema:
  No existe ningún sistema de logging de eventos de seguridad. Para un sitio de
  contenido adulto con pagos planificados esto es insuficiente.

Impacto:
  Sin logging, es imposible detectar intentos de acceso no autorizado, fallos de
  pago fraudulentos, o una brecha de datos (requisito explícito de notificación
  bajo Art. 40 de la Ley 21.719).

Código corregido (lib/logger.ts — estructura para Fase 2):
  type SecurityEvent =
    | 'LOGIN_FAILED'
    | 'LOGIN_SUCCESS'
    | 'PAYMENT_INITIATED'
    | 'PAYMENT_CONFIRMED'
    | 'PAYMENT_FAILED'
    | 'ROLE_CHANGE'
    | 'DATA_EXPORT_REQUESTED'

  export function logSecurityEvent(
    event: SecurityEvent,
    metadata: Record<string, string | number | boolean>
  ) {
    // Nunca loguear: contraseñas, tokens completos, CVV, números de tarjeta
    const sanitized = Object.fromEntries(
      Object.entries(metadata).filter(([k]) =>
        !['password', 'cvv', 'cardNumber', 'token'].includes(k)
      )
    )

    console.log(
      JSON.stringify({
        timestamp: new Date().toISOString(),
        event,
        ...sanitized,
      })
    )
  }

Justificación:
  El logger sanitiza claves sensibles antes de escribir, cumpliendo con el
  principio de minimización de datos (Art. 14 quáter Ley 21.719).

------------------------------------------------------------------------
Archivo: Todo el proyecto — ausencia de app/error.tsx

Problema:
  No hay un app/error.tsx global ni app/global-error.tsx. En Fase 2, los errores

Impacto:
  Information disclosure — un error de Prisma sin capturar puede revelar el

Código corregido (app/error.tsx):
  'use client'

  export default function GlobalError({
    error,
    reset,
  }: {
    error: Error & { digest?: string }
    reset: () => void
  }) {
    return (
      <main className="min-h-screen flex items-center justify-center bg-[#0e0a18]">
        <div className="text-center space-y-4">
          <h1 className="text-white text-2xl font-serif">Algo salió mal</h1>
          <p className="text-[#b3acc4] text-sm">

          </p>
          <button onClick={reset}

Justificación:
  El error.digest es un hash opaco — permite correlacionar el error en logs del

  'use client'
  import { useState, useEffect } from 'react'

  export function AgeGate({ children }: { children: React.ReactNode }) {
    const [verified, setVerified] = useState<boolean | null>(null)

    useEffect(() => {
      setVerified(document.cookie.includes('age_verified=true'))
    }, [])

    const handleConfirm = () => {
      document.cookie = 'age_verified=true; path=/; SameSite=Strict; Secure'
      setVerified(true)
    }

    if (verified === null) return null
    if (verified) return <>{children}</>

    return (
      <div className="fixed inset-0 z-[9999] flex items-center justify-center bg-[#0e0a18]">
        <div className="max-w-sm text-center space-y-6 px-8">
          <h1 className="font-serif text-3xl text-[#D4AF37]">LUXX Producciones</h1>
          <p className="text-[#F5F5F5] text-sm leading-7">
            Este sitio contiene contenido para adultos. Al continuar declaras
            tener 18 años o más.
          </p>
          <div className="flex gap-3">
            <button onClick={handleConfirm}
              className="flex-1 py-3 bg-[#D4AF37] text-black font-bold rounded-xl">
              Soy mayor de 18 años
            </button>
            <a href="https://www.google.com"
              className="flex-1 py-3 border border-white/20 text-white rounded-xl
                         text-sm flex items-center justify-center">
              Salir
            </a>
          </div>
        </div>
      </div>
    )
  }

Justificación:
  La verificación de edad es obligatoria para contenido adulto y refuerza el
  principio de privacidad desde el diseño (Art. 14 quáter). Una cookie de sesión
  es el estándar mínimo; en Fase 2 puede complementarse con verificación de RUT.
